# perpetual — Plan v1.1

A host-side Go CLI (`perpetual`) that boots a Firecracker microVM from a reusable
`agent.ext4` image. Inside the VM runs the native **fx** coding agent
(https://github.com/vercel-labs/fx, the static Linux binary from `releases.fx.sh`,
not any npm package) and a small Go HTTP server (`vmagent`) that owns a SQLite
task queue. The CLI can start a VM from scratch or from a snapshot, kill it,
snapshot it, push tasks in, and trigger a run where fx takes the next task.

This document is the map. Every file the repo will contain is listed with a
skeleton, its pseudocode, and how it connects to the others. Read it top to
bottom once, then use the "Repo layout" section as an index while building.

**This file is also the work log.** Sections 0 to 13 are the plan and change only
when a decision changes. Section 14, "Work state tracker", at the very bottom, is
append-only: whoever does work (you, Claude, or a subagent) appends an entry there
when starting, finishing, or blocking on an item. Because context may be cleared
between sessions and subagents start with no memory, the tracker is the single
source of truth for "where are we". Rule for anyone picking up work: read §14
first, then the milestone table in §10, then the file skeletons you need.

## 1. Goals, non-goals, and definition of done

**Goals (v1)**

1. `make image` produces `images/agent.ext4` (+ `images/vmlinux`) once; it is reused by every VM start.
2. `perpetual vm start` boots a VM from the image; `perpetual vm start --snapshot NAME` restores one.
3. `perpetual vm kill` stops the VM. `perpetual vm status` says what is running.
4. `perpetual vm snapshot NAME` writes `snapshots/NAME/{rootfs.ext4,vmstate.bin,mem.bin,manifest.json}`.
5. `perpetual task add "prompt"` inserts a row into the SQLite queue **inside** the VM over HTTP.
6. `perpetual run` wakes fx: `vmagent` claims the next queued task, runs `fx ask`, and records the outcome as `completed`, `paused`, or `error`.
7. `perpetual task list / task get ID / run get ID / run log ID` read results back out.
8. `perpetual --watch <vm>` (alias `-w`) attaches to sandbox status and output.
   V1 accepts `agent`, its single machine name; unknown names fail clearly.
   Ctrl-C detaches without cancelling execution; watching never starts work.

**Non-goals (v1)** — multiple VMs at once, jailer/seccomp hardening, multi-tenant auth
on the guest API, resumable fx sessions across tasks, a web UI. Each has a
hook noted in §12 so it can be added later without restructuring.

**Done when** the walk-through in §10 passes end to end on this host.

## 2. Decisions and the reasons behind them

| # | Decision | Why | Alternative kept in mind |
|---|---|---|---|
| D1 | **Hand-written Firecracker API client** (`internal/firecracker`) instead of `firecracker-go-sdk` | The SDK v1.0.0 is from 2023 and pins old deps; Firecracker's API is ~8 JSON endpoints over a Unix socket, so writing it yourself is ~250 lines and you will understand every call. It also lets the VMM process be started detached (see D3), which the SDK does not do. | Keep the SDK behind the same interface if the hand-rolled client causes trouble. |
| D2 | **Alpine 3.22 minirootfs** as guest base | Small (~3 MB), `apk` is simple, fx is static so musl vs glibc does not matter. | Debian via `debootstrap` if some fx tool (e.g. `gh`) needs glibc. |
| D3 | **Firecracker runs detached; CLI is short-lived** | Each `perpetual` invocation exits. The VMM must outlive it, so we `setsid` it and remember its PID + socket in `.state/vm.json`. | A long-running host daemon (`agentd`) is the v2 shape; the state file is the seam. |
| D4 | **tap networking with static IPs** (`172.16.0.1` host, `172.16.0.2` guest) + NAT for outbound | Plain HTTP between host and guest; fx needs outbound HTTPS to reach the model API. Guest IP comes from the kernel command line (`ip=`), so the guest has no network scripts. | vsock (no host network config, but HTTP over vsock needs custom dialing). |
| D5 | **Guest DB = SQLite via `modernc.org/sqlite`** (pure Go) | No cgo, so `vmagent` cross-builds to a static binary trivially and runs on Alpine. | `mattn/go-sqlite3` needs cgo + musl toolchain. |
| D6 | **Wake fx with `fx ask --json --full-access`** per task | Simplest headless contract. `--json` gives `final_output` and usage. Full access because there is nobody in the VM to answer permission prompts. | `fx acp` (JSON-RPC over stdio) for streaming and multi-turn — v2, see §12. |
| D7 | **Secret lives only in guest RAM, pushed after boot, scrubbed before snapshot** | The image and snapshots are meant to be shareable, and a Firecracker memory snapshot is a byte copy of guest RAM. See §2.1 for the full reasoning and the lifecycle. | Host-side proxy so the key never enters the VM (v2, §12). |
| D8 | **One run at a time in the guest** | fx is a single workspace agent; serialising avoids two agents editing the same tree. A mutex in `runner` enforces it; `POST /run` returns 409 if busy. | Per-task workspaces later. |
| D9 | **Shared wire types in `pkg/agentapi`**, everything else in `internal/` | Both binaries and any future tool need the same JSON structs and a Go client; that is the one public API of the repo. | — |
| D10 | Repo and module named **`perpetual`**: module `github.com/nickstrad/perpetual`, host CLI binary `perpetual`, guest binary `vmagent` | Your choice of name; Go convention wants a hostable module path. | — |
| D11 | **Provider = Vercel AI Gateway** (`AI_GATEWAY_API_KEY`) | You will have a gateway key, and it is fx's default provider, so no `fx provider` step is needed in the image. | `fx provider codex\|grok` only changes the env var name. |
| D12 | **fx works in `/workspace` inside the image** | Keeps v1 to one drive. A task's optional `repo_url` is cloned under `/workspace/<task-id>`. | Host directory as a second virtio drive (§12). |
| D13 | **Small sizes while we work on UX**: 1 vCPU, 512 MiB RAM, 1 GiB sparse ext4 | Host has only 4 CPUs and 7.8 GiB; fx is 12 MB static and Alpine is ~10 MB with tools. Every size is a single constant in `internal/config`, so growing later is a one-line change. Snapshot `mem.bin` = guest RAM = 512 MiB. | Raise `Machine{VCPUs, MemMiB}` and `SIZE_MB` once UX is settled. |
| D14 | **`vm snapshot` stops the VM** | Snapshot is a "save and put away" action, not a checkpoint of a running system. Stopping also removes the question of what happens to the scrubbed secret in the still-running guest. Order: scrub secret → pause → copy disk → create snapshot → kill. | A `--keep-running` flag later if checkpoints turn out useful. |

**Resolved in this revision:** name (D10), provider (D11), workspace (D12), sizes (D13),
snapshot-stops (D14). No open questions remain for v1.

### 2.1 Getting the gateway key into the VM (D7 in depth)

The question is "where can the secret be, and who can read it there". Ranked from
worst to best for our setup:

| Where the key could live | Who can read it | Verdict |
|---|---|---|
| Kernel boot args (`boot_args`) | anyone with `cat /proc/cmdline` in the guest, the Firecracker log, `ps` on the host | never |
| Baked into `agent.ext4` at build time | anyone who gets the image or any snapshot's `rootfs.ext4` | never; the image is meant to be shareable |
| `.env` on the host, read by the CLI | only the host user (file mode `0600`) | fine, this is the source of truth |
| Guest RAM, held by `vmagent`, passed to `fx` as an env var | a process inside the guest; **and `mem.bin` of any snapshot taken while it is resident** | v1 choice, with the scrub rule below |
| MMDS (Firecracker's built-in metadata service at `169.254.169.254`, populated via `PUT /mmds`) | the guest via HTTP; also saved inside `vmstate.bin` on snapshot | idiomatic Firecracker, same snapshot caveat; a good v2 study item |
| Never in the VM: a host-side proxy injects the key into outbound model requests | only the host | best; needs fx to support a custom gateway base URL, unverified (§12) |

**Lifecycle we implement (v1)**

1. Host: `perpetual` reads `.env` (`AI_GATEWAY_API_KEY`, optional `FX_MODEL`). The CLI refuses to start if `.env` is group/world readable, mirroring what `ssh` does with keys.
2. Transport: `POST /config` over the tap link. The link is a point-to-point virtual cable between the host kernel and the guest; no other machine is on it, so plain HTTP is acceptable here. (If the guest API is ever exposed beyond tap0, add TLS or a token first.)
3. Guest: `vmagent` keeps the value in a `map[string]string` guarded by a mutex. It is never written to disk, never logged, and the `/config` handler logs only key *names*. `fx` receives it as an environment variable of the child process only. `FX_TRACE_LOG` stays off by default because trace logs could echo request headers.
4. Health reporting: `GET /healthz` returns `has_secret: true|false` so the CLI can tell you when a restore is missing its key, without revealing the value.
5. Scrub before snapshot: `perpetual vm snapshot` first calls `DELETE /config`. The handler clears the map, and Go's `clear()` on the map plus a zeroing loop over the byte slices drops the plaintext before the pause. This is best effort (Go's garbage collector may leave copies), which is why the snapshot is also stored under `snapshots/` with mode `0700` and treated as sensitive anyway.
6. Restore: `perpetual vm start --snapshot NAME` pushes the key again after the health check, exactly like a fresh boot. A restored VM without a key shows `has_secret=false` and a run would fail with `auth=missing`, so the CLI checks and pushes before returning.

What you learn from this: secrets have a *lifecycle* (source → transport → residency → erasure), and each stage has a different reader to defend against. The snapshot step is the one people forget.

## 3. Concepts you will meet (plain-language glossary)

- **microVM / Firecracker** — a very small virtual machine. Firecracker is a program (the "VMM", virtual machine monitor) that asks the Linux KVM feature to run a guest kernel. You configure it by sending HTTP requests to a Unix socket *before* the VM starts, then say "start".
- **Kernel + rootfs** — a VM needs (a) a Linux kernel file (`vmlinux`) and (b) a disk image with a filesystem on it (`agent.ext4`). ext4 is just a normal Linux filesystem stored inside a single file.
- **Loop mount** — `mount -o loop agent.ext4 /mnt/x` lets the host treat the file as a disk so we can copy files into it while building.
- **init** — the first process the guest kernel starts (PID 1). Ours is a shell script that mounts `/proc`, `/sys`, sets DNS, and execs `vmagent`. No systemd/openrc, so it is readable.
- **tap device** — a virtual network cable. One end is a Linux interface on the host (`tap0`), the other is `eth0` in the guest. Giving each end an IP lets host and guest talk.
- **NAT / MASQUERADE** — iptables rule that lets the guest's packets go out through the host's real interface so fx can reach the internet.
- **Snapshot** — Firecracker can freeze a VM and write its RAM (`mem.bin`) and device state (`vmstate.bin`) to files. Together with a copy of the disk at that instant, the VM can be brought back exactly where it was in ~100 ms.
- **Cobra** — Go library for building CLIs with subcommands (`perpetual vm start`), flags, and help text.
- **`cmd/`, `internal/`, `pkg/`** — Go repo convention. `cmd/<name>/main.go` is one executable each and stays tiny. `internal/` is code only this module may import (compiler enforces it). `pkg/` is code other modules may import.
- **SQLite as a task queue** — one table of tasks with a `status` column. "Claiming" a task is a single `UPDATE ... WHERE status='queued' ... RETURNING` so two callers can never take the same one.
- **Static binary** — an executable with no external library dependencies; it runs on any Linux. Both fx and our `vmagent` (`CGO_ENABLED=0`) are static.

## 4. Architecture

```
HOST (this droplet)                                    GUEST (Firecracker microVM)
┌───────────────────────────────────────┐              ┌──────────────────────────────────┐
│ perpetual (cobra CLI, short-lived)     │              │ /sbin/init (shell)               │
│   vm start|kill|status|snapshot       │              │   └─ vmagent  :8080 (Go HTTP)    │
│   task add|list|get                   │   HTTP over  │        ├─ queue  (SQLite file)   │
│   run [trigger]|get|log               │   tap0 ⇄ eth0│        └─ runner ─exec─► fx ask   │
│                                       │ ───────────► │                    (cwd=/workspace)
│ internal/vm  ── internal/firecracker ─┼─ unix sock ─►│ firecracker process (VMM)        │
│ internal/net (tap, NAT)               │              └──────────────────────────────────┘
│ .state/vm.json  (pid, socket, ip)     │
│ images/agent.ext4, images/vmlinux     │      NAT ──► internet (model API)
│ snapshots/<name>/{rootfs,mem,vmstate} │
└───────────────────────────────────────┘
```

Two independent channels:

1. **Control plane** — `perpetual` → Firecracker API socket (`.state/firecracker.sock`). Used only for start/pause/snapshot/stop.
2. **Data plane** — `perpetual` → `http://172.16.0.2:8080` (`vmagent`). Used for tasks, runs, config.

### 6.7.1 `internal/cli/watch.go`

`perpetual --watch agent` and `perpetual -w agent` select the running sandbox.
Reject unknown names and fail clearly when the machine has stopped.
V1 polls existing health, task, run, and log endpoints once per second.
Find the running task and follow its `last_run_id` using log offsets.
Show status, replay available output, then follow new output without duplicate bytes.
Drain the previous run's remaining log before switching to another run.
Wait when idle and follow subsequent runs until the user detaches.
Ctrl-C cancels local polling only; guest execution continues.
Report connection loss clearly and allow users to attach again.
Watch provides output viewing, without shell access or interactive input.

[V1.3 architecture](v1.3_architecture.md) routes this command through `agent-plane` using optional WebSockets.
V1 retains its existing direct guest connection and single-machine scope.

type Process struct { PID int; Socket string }

// Spawn starts `firecracker --api-sock <sock> --id <id>` detached from our session
// so it survives perpetual exiting (D3). Console (guest serial) goes to consoleLog.
func Spawn(binary, socket, consoleLog string) (*Process, error) {
    os.Remove(socket)
    cmd := exec.Command(binary, "--api-sock", socket, "--id", "agent")

    cmd.Start(); cmd.Process.Release()
    waitForSocket(socket, 3s)
    return &Process{PID: cmd.Process.Pid, Socket: socket}
}

func (m *Manager) Start(ctx, StartOpts) (*State, error) {
    if st := state.Load(); st != nil && alive(st) { return error "VM already running (pid N); run `vm kill`" }
    preflight: /dev/kvm rw, kernel + image exist, firecracker on PATH

    fc.SetBootSource({kernel, cfg.KernelArgs()})

    fc.AddNetworkInterface({"eth0", MAC, tap})

}

### 6.16 `internal/vm/snapshot.go`

```go
type Manifest struct {
    Name string; CreatedAt time.Time
    FirecrackerVersion, KernelSHA256, ImageSHA256 string
    VCPUs, MemMiB int; Tap, GuestIP, MAC string
    Files struct{ Rootfs, Mem, Vmstate string }
}

// Snapshot always ends with the VM stopped (D14). The caller has already asked
// the guest to scrub its secret (§2.1) so mem.bin does not carry the key.
func (m *Manager) Snapshot(ctx, name string, force bool) (*Manifest, error) {
    st := running state or error
    dir := snapshots/name ; mkdir 0700 (error if exists unless force)
    fc.Pause()                                    // freeze so disk + memory are consistent
    copyFile(WorkRootfs → dir/rootfs.ext4)        // disk as of the pause
    fc.CreateSnapshot({Full, dir/vmstate.bin, dir/mem.bin})
    write manifest.json
    m.Kill(ctx)                                   // stop VMM, remove tap, clear .state
    return manifest
}
```
Why pause before copying: Linux in the guest may have dirty pages not yet flushed
to the virtual disk; the memory snapshot carries those, and the disk copy must
match the same instant. Why stop afterwards: the saved state and the live VM would
otherwise diverge immediately, and "snapshot" would mean two different things.

func (h *handlers) triggerRun(w, req) {
    task, run, err := h.q.ClaimNext(ctx)
    if errors.Is(err, queue.ErrEmpty) { w.WriteHeader(204); return }
    err = h.r.TryStart(func() {
        out := h.r.Execute(context.Background(), task, run)   // detached from the request
        h.q.FinishRun(ctx, run.ID, out)

    if errors.Is(err, runner.ErrBusy) { h.q.Unclaim(task) ; writeJSON(409, …) ; return }   // put it back
    writeJSON(202, run)
}

## 7. Guest HTTP API (the contract)

| Method & path | Body → Response | Status codes |
|---|---|---|
| `GET /healthz` | → `Health` | 200 |
| `POST /config` | `Config{env}` → 204 | 204 |
| `DELETE /config` | → 204 (scrub secrets from memory) | 204 |
| `POST /tasks` | `NewTask` → `Task` | 201, 400 |
| `GET /tasks?status=` | → `[]Task` | 200 |
| `GET /tasks/{id}` | → `Task` | 200, 404 |
| `POST /run` | → `Run` | 202 started, 204 nothing queued, 409 busy |
| `GET /runs/{id}` | → `Run` | 200, 404 |
| `GET /runs/{id}/log?offset=N` | → text/plain bytes from offset | 200, 404 |

State machine for a task: `queued → running → completed | paused | error`.
`paused` tasks can be re-queued by a future `task retry` command (§12).

## 8. End-to-end flows

**vm start (from scratch)**
1. `cli/vm.go` → `Manager.Start`: preflight → copy image → tap/NAT → spawn firecracker → 4 PUTs + InstanceStart → save state.
2. Guest kernel boots (~1 s), `init.sh` execs `vmagent`.
3. CLI polls `GET /healthz` until 200, then `POST /config` with the API key.
4. Prints status. Total target: < 5 s.

**task add** → `POST /tasks` → row in `queue.db` with `status=queued`.

**watch**: `perpetual -w agent` follows sandbox status and output until detachment.
The guest continues execution after Ctrl-C; reattachment replays available output.

**run**
1. `POST /run` → `ClaimNext` (`queued→running`, run row) → `TryStart` goroutine → 202.
2. Goroutine: `fx ask --json --full-access -- <prompt>` in `/workspace`; stdout/stderr to `/var/lib/vmagent/runs/<id>.log`.
3. `classify` → `FinishRun` sets run + task to `completed|paused|error`.
4. `perpetual run --wait` polls `GET /runs/{id}` and prints `final_output`.

**vm snapshot NAME** → `DELETE /config` (scrub key) → pause → copy `.state/rootfs.ext4` → `/snapshot/create` → `manifest.json` → kill VM (D14). The queue DB, fx sessions, and workspace are all inside the ext4, so they travel with the snapshot. Refuses if a run is in progress (`/healthz` reports `busy`), because a half-finished fx process is not worth saving.

**vm start --snapshot NAME** → verify manifest version → copy rootfs → tap with the **same name and IP** (Firecracker requires the tap to exist under the saved name) → spawn → `/snapshot/load` with `resume_vm=true` → health check shows `has_secret=false` → `POST /config` pushes the key again → ready.

**vm kill** → `SendCtrlAltDel` (guest init ignores it in v1, so falls through) → SIGTERM → SIGKILL → remove tap → clear state.

## 13. Risks and how the plan handles them

- **fx JSON / pause semantics are undocumented** → M4 discovery step captures real output into fixtures before `classify` is finalised.
- **Snapshot restore requires identical Firecracker version, kernel, and tap name** → `manifest.json` records them; `StartFromSnapshot` checks and refuses with a clear message.
- **Guest clock after restore is stale** → `init.sh` is not re-run; if TLS fails after long-lived snapshots, add `POST /config` → `date -s` from host time (small handler).
- **Running as root on the host** → accepted for v1; documented; jailer later.
- **Memory: 512 MiB guest + 512 MiB snapshot file** → comfortable on the 7.8 GiB host; if fx runs out of memory on a real repo, the symptom is the guest kernel's OOM killer in `.state/console.log`, and the fix is one constant (D13).
- **Secret in snapshot RAM** → scrubbed before pause and verified by the M5 `strings | grep` check; snapshots dir is `0700` and gitignored regardless.
- **fx auto-upgrade or telemetry from inside the VM** → `FX_AUTO_UPGRADE=0` and `auto_upgrade:false` in settings; egress stays open only because the model API needs it.
