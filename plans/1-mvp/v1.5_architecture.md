# V1.5 architecture

A sandbox is a disposable virtual machine containing programs and working files.
A control plane manages sandbox creation, addresses, lifecycle, and requested actions.
`agent-plane` provides that control plane for one or many sandboxes.
`vmagent` exposes an HTTP/HTTPS server inside each sandbox to execute tool calls.
A tool call requests an action, such as running commands or reading files.
HTTP carries individual requests and responses; polling repeats requests to observe changes.
HTTPS encrypts HTTP traffic.
A WebSocket upgrades an HTTP connection for ongoing communication in both directions.
Secure WebSockets use HTTPS for that upgrade.
A transaction groups related database changes into one committed outcome.
PostgreSQL is a database server supporting concurrent transactions.
It stores machine records and action history on the host.
Firecracker creates and runs the virtual machines.
SSH provides direct terminal access to a running sandbox.
A snapshot saves machine memory and disk for later restoration.

```text
 Caller: CLI or HTTP client
       |
       | HTTP requests and responses
       v
+-----------------------------------------------------------------------+
| HOST                                                                  |
|                                                                       |
| agent-plane                                                           |
|      |                                                                |
|      +<----> PostgreSQL: machines, addresses, lifecycle, actions        |
|      +<----> Host files: images, snapshots, collected output            |
|      |                                                                |
|      +-- lifecycle --> Firecracker --> sandbox 1 ... sandbox N         |
|      |                                                                |
|      +-- HTTP/HTTPS actions; optional WebSocket upgrade --------+       |
+---------------------------------------------------------------|-------+
                                                                |
                                 +------------------------------|-------+
                                 | SANDBOX                      v       |
                                 | vmagent: HTTP/HTTPS tool server      |
                                 |    |                                 |
                                 |    +--> commands and child processes |
                                 |    +--> file reads and writes        |
                                 |    +--> action records and output    |
                                 |                                      |
                                 | SSH server --> interactive shell     |
                                 +-------^------------------------------+
                                         |
 User terminal -- SSH through host ------+

 Lifecycle: create / start / inspect / stop / delete / snapshot / restore
 Actions: execute / inspect action / read output / cancel / read or write file
```

## Scope and ownership

The platform accepts concrete actions without interpreting prompts or choosing subsequent work.
`agent-plane` owns machine lifecycle, address routing, and the host database.
PostgreSQL runs separately; stopping the control plane leaves the database running.
Concurrent workers use bounded database connections and short transactions.
Ownership constraints prevent conflicting machine operations.
`agent-plane` forwards tool calls to the selected sandbox's `vmagent` server.
`vmagent` executes actions and tracks their local processes, results, and output.
It never pulls tasks or schedules autonomous work.

Machine records include identity, guest endpoint, SSH port, and lifecycle status.
The guest endpoint records its HTTP or HTTPS scheme, address, and port.
Machine records also track boot identity, creation time, last contact, and snapshot origin.
The host distinguishes requested changes from confirmed machine state.
New boot identities prevent old action reports from changing restored machine records.

The control plane checks guest health and actions through HTTP or HTTPS.
It can upgrade selected connections to WebSockets for ongoing command output.
Guests need no callback endpoint; connections originate from `agent-plane`.
Security hardening remains outside this architecture pass.

## Connections

Routine actions use request/response; longer commands can optionally use WebSockets.
HTTP endpoints support ordinary WebSockets; HTTPS endpoints support secure WebSockets.
An upgrade affects one connection, leaving other requests unchanged.
Long commands still work through polling when upgrades remain unavailable.

First, submit the command through HTTP or HTTPS and obtain its action identifier.
Then, optionally upgrade a separate connection to follow that existing action.
The upgrade attaches to execution; it never starts another command.
The connection carries output, status, and supported command input in both directions.
Cancellation also remains available through an ordinary HTTP request.

Closing a WebSocket leaves execution running; reconnect using the same action identifier.
Numbered output chunks support replay after the last received position.
Bounded buffers prevent slow readers from blocking execution and report discarded output.
Close the connection after collecting completion; no permanent stream remains necessary.

The CLI continues using request/response with `agent-plane`, including watch polling.
The control plane stores guest output for those requests, regardless of guest transport.
SSH remains the path for interactive terminals.

## Actions and execution

1. The caller selects a sandbox and submits a concrete action.
2. `agent-plane` records its identifier and forwards the request to `vmagent`.
3. File operations return bounded results; command execution returns an action identifier promptly.
4. The guest runs the command independently of the originating HTTP request.
5. The caller polls through `agent-plane` for status, output chunks, and exit code.
6. The control plane collects completion independently of whether the caller remains connected.

Command requests specify executable, arguments, working directory, and optional execution timeout.
Explicit cancellation targets an action and its child processes.
Closing the CLI or an HTTP request never cancels accepted execution.
Retries reuse action identifiers; guests return known outcomes instead of repeating accepted actions.
Uncertain starts require inspection before retrying with a new identifier.

The first implementation allows one active platform command per sandbox.
File operations remain available; different sandboxes can execute commands concurrently.

## SSH and watch

`perpetual ssh <vm>` requests connection details from `agent-plane`, then launches local SSH.
Local users connect to the guest address directly.
Remote users connect through the host using SSH's jump-host option.
The sandbox image starts an SSH server alongside `vmagent` and configures login access.
SSH traffic bypasses the control plane after address discovery.

Use SSH for interactive programs, debugging, manual edits, and large file transfers.
The platform does not record SSH activity as tool actions.
Users manage SSH session persistence themselves.

`perpetual --watch <vm>` and `perpetual -w <vm>` poll sandbox and action status.
Watch retrieves bounded output chunks through `agent-plane` using saved positions.
Ctrl-C stops viewing while accepted actions continue.

## Lifecycle and recovery

Fresh sandboxes boot writable copies of a reusable image.
Stopping interrupts guest programs; deletion removes the working disk.
Explicitly saved snapshots remain separate from sandbox deletion.
Automatic expiration remains deferred; callers stop or delete sandboxes explicitly.

Snapshots block new actions and wait for existing commands and file writes.
They stop the sandbox after saving; restoration opens fresh connections.
Users must finish interactive SSH work before snapshotting.
The platform cannot infer safe snapshot boundaries from untracked SSH activity.

Control plane outages delay observation but leave running guests executing.
Recovery inspects surviving machines and actions before accepting conflicting work.
Missing health responses mean unreachable, not confirmed stopped.
Guests retain bounded output and report gaps when older chunks expire.
Machine loss before collection can lose action results and output.
Database outages block new durable mutations but leave accepted guest commands running.
Recovery reconnects and reconciles uncertain commits before dispatching dependent work.

## Biggest concerns

- Lost responses make execution uncertain; retries must avoid repeating file or command mutations.
- SSH users can change files while platform actions use them.
  Users must coordinate manual work with automated calls.
- Restoring snapshots rewinds guest files while host history continues forward.
  Restoration must reconcile action records and distinguish the new boot.
- Concurrent database writes still need explicit ownership checks and bounded lock waits.

## Pros

- A small tool interface supports different callers without embedding their workflows.
- Direct SSH provides interactive access without building terminal relaying.
- Independent execution supports disposable callers and long commands.
- PostgreSQL supports concurrent state updates across independent machines.

## Cons

- Supporting polling and WebSockets adds connection recovery and output ordering work.
- Polling delays updates and adds requests across many sandboxes.
- SSH changes bypass action history and command scheduling.
- Images must include `vmagent`, an SSH server, and required execution tools.
- PostgreSQL adds service setup, backups, and database failure handling.

This proposal replaces [v1.4](v1.4_architecture.md) with lifecycle management and concrete tool actions.
