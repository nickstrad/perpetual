# V1.4 architecture

The host runs `perpetual`, the command-line tool, and the background service `agent-plane`.
A control plane coordinates machines, commands, and recorded state.
A sandbox is a virtual machine containing programs and their working files.
Each sandbox runs `vmagent`, which owns execution and reports its state.
SQLite stores the host's machine registry, task queue, and run history.
HTTP lets one program send a request and receive a response.
Polling repeats requests periodically to discover changes.
Firecracker manages sandbox machines; other machine managers could follow later.

 A: execute next task, cancel run, fetch status, fetch output chunk

 Every request receives a response through its originating connection.
 Neither direction requires a permanent connection.

## Ownership and routing

The CLI always talks to `agent-plane`; every interaction uses HTTP request/response.
This version uses no WebSockets or streaming responses.
The control plane exposes a reachable HTTP port for registered guests.
It routes guest commands using each machine's recorded address and port.
It also manages machine creation, stopping, and restoration through Firecracker.

Only `agent-plane` writes the host database.
CLI commands change requested state; guest reports change observed state.
Machine records include identity, address, lifecycle status, creation time, and last contact.
They also include boot identity, active run, and snapshot origin.
The host assigns new boot identities after restart or restoration.
It rejects reports from previous boots.

## Task execution

1. The CLI submits a task; `agent-plane` saves it in the host queue.
2. A run command asks `agent-plane` to request execution from the selected guest.
3. `vmagent` acknowledges acceptance promptly, then requests the next task through HTTP.
4. The host claims one task and returns its run identifier and instructions.
5. The guest records acceptance locally and starts execution independently of HTTP connections.
6. It periodically posts health, progress, and bounded output chunks to `agent-plane`.
7. It posts the final result; the host saves it before acknowledging receipt.

An empty queue returns no task; this version requires another explicit run command.
Each sandbox executes one task at a time; different sandboxes can work concurrently.
Retries reuse command and claim identifiers to prevent duplicate starts or claims.
The host records claims atomically, preventing two guests from receiving the same task.
Acceptance confirms receipt, not successful task completion.

## Watch and cancellation

`perpetual --watch <vm>` and `perpetual -w <vm>` poll `agent-plane` once per second.
Watch displays status and requests output after its last received position.
The control plane serves stored output and fetches missing retained chunks through HTTP.
Each response contains a bounded chunk and the next position.
Watch waits when idle and follows subsequent runs without starting work.
Ctrl-C stops polling; it leaves guest execution running.
Cancellation requires a separate command and the guest's confirmation.

## Recovery

Execution continues after CLI disconnection or control plane failure.
Guests retain unacknowledged results and bounded output locally, then retry delivery.
Numbered updates let the host reject duplicates and stale reports.
Guests report missing output when retention limits remove older chunks.
Missed health reports mean unreachable, not confirmed stopped.
The host reconciles uncertain commands and runs before assigning replacement work.

## Biggest concerns

- Lost responses can hide successful execution or task claims.
  Persist request identities and outcomes before acknowledging state changes.
- Both sides expose HTTP servers, requiring reachable addresses and authenticated requests.
  Restrict guest reports to their assigned machine and current boot.
- Control plane outages block commands and delay results despite continued guest execution.
  Guest loss before upload can permanently lose results and output.
- Restoring a sandbox can rewind files while host history remains current.
  Reconcile restored state and back up host records separately.

## Pros

- Ordinary HTTP requests simplify debugging, timeouts, and connection management.
- Independent execution lets users detach without interrupting work.
- Host records provide one view across many sandboxes.

## Cons

- Polling adds delay and repeated requests, especially with many viewers.
- Interactive terminal sessions need a later design.
- Arbitrary images still need compatible `vmagent` installation and guest networking.

This proposal replaces [v1.3](v1.3_architecture.md) with request/response communication throughout.
