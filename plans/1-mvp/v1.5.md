## 1. Goals, exclusions, and completion

### Goals

1. Build `perpetual`, `agent-plane`, and `vmagent` as separate Go binaries.
2. Build a reusable guest image containing tool execution and SSH services.
3. Manage multiple named machines through one host control plane.
4. Persist machine identities, addresses, lifecycle operations, and action records on the host.
5. Execute commands and bounded file operations through HTTP or HTTPS.
6. Optionally upgrade selected guest connections to WebSockets for command output and input.
7. Preserve guest execution when callers disconnect or the control plane restarts.
8. Support `perpetual --watch <vm>` and `perpetual -w <vm>` through polling.
9. Support `perpetual ssh <vm>` for direct interactive access.
10. Snapshot idle machines, stop them, and restore them with fresh connection state.
11. Report uncertain operations honestly and avoid automatic duplicate execution.
12. Make core behavior testable without root privileges, live guests, or external services.
13. Grow a custom simulator alongside shared production coordination, starting with admission.

### Exclusions

Prompt interpretation, autonomous scheduling, and caller-specific workflows remain outside the platform.
Security hardening, tenant isolation, and permission systems remain deferred.
HTTPS supports configured certificates; certificate issuance remains an operator responsibility.
The CLI never opens WebSockets; only the control plane uses guest upgrades.
Interactive terminal emulation belongs to SSH.
Automatic expiration, live migration, snapshot cloning, and multiple control-plane hosts remain deferred.
Arbitrary guest images require compatible services and the documented boot contract.

### Definition of done

Every milestone in section 10 must record its verification evidence in section 14.
Two machines must run independently without address, process, or disk collisions.
Both polling and streaming must pass the same command outcome checks.
The walkthrough must survive detachment, control-plane restart, and snapshot restoration.
No implementation milestone starts complete merely because its files exist.
Each milestone must also pass its testability review from section 11.

## 2. Decisions and ownership

| ID | Decision | Reason |
| --- | --- | --- |
| D1 | One background `agent-plane` per host | Central ownership prevents competing machine controllers. |
| D2 | Host PostgreSQL with bounded concurrent connections | Independent workers can persist state without one database writer bottleneck. |
| D3 | Thin Firecracker HTTP client over local sockets | Keep machine configuration and process ownership explicit. |
| D4 | Detached machine processes with recorded process identity | Control-plane shutdown must leave guests running. |
| D5 | One writable disk copy and network allocation per machine | Machines must not share mutable runtime resources. |
| D6 | HTTP by default; configured HTTPS optional | Routine actions need only request/response. |
| D7 | WebSocket attachment follows command creation | Connection recovery must never restart execution. |
| D8 | One active platform command per guest | Keep process ownership and cancellation straightforward. |
| D9 | File operations remain available during commands | Callers may inspect or exchange working files. |
| D10 | Guest journals record actions, without a guest task database | Preserve retry evidence without introducing scheduling. |
| D11 | Explicit action identifiers and request fingerprints | Retries must distinguish duplicates from conflicting requests. |
| D12 | Host polling collects results without attached viewers | CLI lifetime must not determine record completeness. |
| D13 | SSH handles interactive work | Avoid terminal relaying and shell session management. |
| D14 | Snapshots drain platform actions and then stop guests | Save one consistent execution boundary. |
| D15 | Restore the original stopped machine identity | Preserve saved paths and networking without implementing cloning. |
| D16 | Every start or restoration creates a new boot identifier | Reject stale observations and separate historical actions. |
| D17 | Explicit stop before delete | Keep data removal distinct from process termination. |
| D18 | Resource ceilings apply across the host | Multiple small guests can still exhaust host resources. |
| D19 | Custom event simulator runs shared production decisions | Teach reproducible recovery testing without emulating entire machines. |

### Responsibility boundaries

- `perpetual` formats requests, displays responses, polls output, and launches the SSH client.
- `agent-plane` owns PostgreSQL records, machine lifecycle, routing, reconciliation, and output collection.
- PostgreSQL runs independently on the host; workers share a bounded connection pool.
- Firecracker owns virtual machine execution on the host.
- `vmagent` owns concrete actions, child processes, local output, and retry records.
- Guest initialization starts services, configures networking, and reaps orphaned processes.
- SSH users own interactive sessions and coordination with platform actions.

Stopping `agent-plane` closes its connection pool after saving progress.
It never stops the PostgreSQL service.
It never stops guest machines as an incidental cleanup action.
Only explicit machine operations may terminate them.

## 3. Terms and runtime defaults

A sandbox is a virtual machine containing programs and working files.
A control plane coordinates machine lifecycle and requested actions.
A tool call requests a concrete action, such as executing a command.
An operation tracks a lifecycle change that can outlast an HTTP request.
A boot identifier distinguishes separate executions of the same machine.
A journal records accepted actions and outcomes durably inside the guest.
A request fingerprint hashes the normalized action parameters.
Reconciliation compares stored expectations against actual processes and guest reports.
A cursor identifies the next output event a reader needs.
A transaction commits related database changes together.
PostgreSQL is the host database server; a connection pool reuses bounded database connections.
A tap interface connects guest networking to the host.
Address translation lets guests access external networks through the host.
A snapshot contains saved memory, device state, and matching disk contents.
Quiescing blocks new actions and waits for existing platform work to finish.
HTTP carries request/response; HTTPS encrypts that connection.
A WebSocket upgrades one connection for messages in both directions.
SSH provides a direct interactive terminal connection.

These initial defaults remain configurable and require validation during implementation.

| Setting | Initial value |
| --- | --- |
| Control-plane listener | `127.0.0.1:7777` |
| Database connection | Required configuration; dedicated PostgreSQL database on the host |
| Database pool | At most eight connections initially; configurable |
| Database statement and lock limits | Five seconds and one second initially; validate during M1 |
| Guest tool listener | `:8080` |
| Guest SSH port | `22` |
| Guest resources | One virtual CPU, 512 MiB memory, 1 GiB disk |
| Host admission ceiling | Two running machines initially; configurable memory budget |
| Network pool | Configured private IPv4 pool; reject conflicting host routes |
| Machine network | Unique `/30` subnet, tap name, guest address, and MAC address |
| Health and CLI watch polling | One second |
| Command status collection | One second while active; slower health polling while idle |
| Ordinary HTTP timeout | Five seconds |
| Guest readiness timeout | Thirty seconds |
| Command execution timeout | None unless the caller specifies one |
| Snapshot drain timeout | Thirty seconds unless explicitly overridden |
| Command output retention | 16 MiB per action; configured aggregate guest limit |
| Output response size | At most 64 KiB payload bytes |
| File read/write size | At most 1 MiB per request |
| WebSocket message size | At most 64 KiB decoded payload |
| stdin input request | At most 64 KiB; explicit end-of-input support |

A host lock prevents two control-plane processes from opening the same runtime root.
Keep one control plane per host; concurrent database connections do not change ownership.
Assign its database to one runtime root; sharing databases across hosts remains unsupported.
Address allocations remain reserved while their machine or saved snapshots need them.
Resource admission counts starting, running, restoring, and stopping machines.
Unknown machines retain reservations until reconciliation proves their resources available.

## 4. Architecture and durable records

```text
 CLI / HTTP client
        |
        | request/response
        v
 agent-plane ---- PostgreSQL: machines, operations, actions, snapshots, allocations
        |  \----- Host output files and collection cursors
        |
        +-------- Firecracker processes ---- guest machines
        |
        +-------- HTTP/HTTPS; optional WebSocket ---- vmagent
                                                       |
                                                       +-- commands and files
                                                       +-- journal and output

 User terminal -------- SSH through host -------- guest SSH server
```

### Host records

Use structured columns for identifiers, state, timestamps, and fields used during recovery.
Use JSON only for variable command parameters and operation details.
Store timestamps in UTC and counters as integers.
Use PostgreSQL `jsonb`, `timestamptz`, and checked `bigint` columns for those respective values.
Reject counters beyond signed database ranges before persistence.

```text
machines
  id, name UNIQUE, desired_state, observed_state, revision
  boot_id, guest_instance_id, guest_url, ssh_user, ssh_port
  image_id, kernel_path, rootfs_path, runtime_dir
  vcpus, memory_mib, pid, process_start_ticks, socket_path
  allocation_id, source_snapshot_id
  created_at, updated_at, last_seen_at, deleted_at, last_error

operations
  id PRIMARY KEY, machine_id, kind, request_fingerprint
  status, phase, details_json, error, created_at, finished_at
  UNIQUE active lifecycle operation per machine

actions
  id PRIMARY KEY, machine_id, boot_id, guest_instance_id
  kind, request_fingerprint, request_json, status
  accepted_at, started_at, finished_at, exit_code, error
  collected_through_seq, available_from_seq, final_seq, output_complete
  UNIQUE active command slot per machine

snapshots
  id PRIMARY KEY, name UNIQUE, machine_id, source_boot_id
  status, directory, manifest_json, created_at, last_error

allocations
  id PRIMARY KEY, machine_id UNIQUE, subnet UNIQUE
  tap_name UNIQUE, guest_ip UNIQUE, host_ip, mac UNIQUE

host_capacity
  singleton_id PRIMARY KEY CHECK singleton_id = 1
  reserved_machines, reserved_memory_mib, revision

schema_migrations
  version PRIMARY KEY, applied_at
```

Use database transactions to reserve command slots and lifecycle ownership.
Lock the machine row before checking lifecycle admission and reserving command ownership.
Use Read Committed isolation with explicit row locks for these transactions.
Read Committed exposes committed data but does not serialize multistep admission checks.
Recheck conditions after acquiring locks; enforce uniqueness in the database too.
Use partial unique indexes for active commands and lifecycle operations.
Their predicates must include uncertain states that retain ownership.
Lock shared host capacity before machine rows when admission spans host resources.
Record capacity in a dedicated singleton row, updated within the reservation transaction.
Use consistent lock ordering and bounded waits; keep unrelated machine updates independent.
Retry confirmed transaction aborts within bounds, preserving identifiers and request fingerprints.
Resolve unknown commit outcomes through inspection; never infer rollback from connection loss.
A missing row alone cannot exclude an earlier transaction still committing.
Reconcile through the same identifier and conflicting reservation locks before dispatching work.
Never hold a transaction open while calling the guest or Firecracker.
Persist intended operations before performing their external effects.
Record operation phases after confirmed effects; recovery must tolerate gaps between both.
Missing completion evidence means uncertain, not failed or safe to repeat.
These rules follow PostgreSQL's [isolation](https://www.postgresql.org/docs/current/transaction-iso.html) and [locking](https://www.postgresql.org/docs/current/explicit-locking.html) semantics.

### Guest records

```text
/var/lib/vmagent/
  identity.json                  machine, boot, and guest-process identities
  actions/<action-id>/
    request.json                 immutable fingerprint and request
    status.json                  acceptance, process identity, result
    input.json                   input sequence and uncertain delivery
    events/<segment>.jsonl       bounded, numbered output events
```

Write metadata through temporary files, flush them, then rename them atomically.
Sync containing directories when publishing durable acceptance or final outcomes.
Keep final outcomes separately from removable output segments.
Retain action identifiers for the boot's lifetime, even after output expires.
Reject new actions when metadata limits prevent preserving retry evidence.
Guest restart creates a new guest-process identity and marks unfinished actions uncertain.
It must not automatically execute accepted journal entries again.

### 6.7 `internal/plane/service.go`, `server.go`, and `handlers.go`

`service.go` wires dependencies and owns background worker lifetimes.
`server.go` registers host routes from section 7 and configures bounded HTTP requests.
`handlers.go` validates identities, request sizes, revisions, and supported operations.
Accept operations durably, then hand them to workers independent of request contexts.
Never block lifecycle admission while holding a database transaction across external calls.
Return recorded outcomes for duplicate identifiers with matching fingerprints.
Return conflicts when reused identifiers contain different requests.
Route admission decisions through `internal/control`; handlers must not duplicate those rules.
Service workers execute requested effects and return typed completion events.
Keep external work concurrent, with bounded capacity and independent per-machine progress.
Never wait for network completion inside the shared decision function.

The service tracks upgraded guest connections separately during shutdown.
Go's HTTP shutdown does not close upgraded connections automatically.
See [Go's HTTP server documentation](https://pkg.go.dev/net/http#Server.Shutdown).

### 6.8 `internal/plane/dispatch.go`

```go
Dispatch(machineID, request):
    return matching existing action before checking admission or command-slot availability
    require ready machine; reserve action and command slot when applicable
    persist normalized request and fingerprint
    send request with machine ID, boot ID, and action ID
    save guest acceptance or definite rejection
    on ambiguous delivery: mark uncertain; inspect same action ID
    never replace an uncertain action with a new identifier
```

Dispatch concrete execution, file, input, and cancellation requests only.
Retries must use the same boot identity and request fingerprint.
Guest rejection before acceptance may release the command slot.
A guest-process identity change prevents blind replay of unfinished work.

### 6.9 `internal/plane/collect.go` and `output.go`

`collect.go` polls active actions even when no CLI remains attached.
With `poll`, always fetch bounded event pages.
With `stream`, attempt attachment and report unsupported upgrades clearly.
With `auto`, prefer streaming for ongoing output and fall back to polling.
Failed stream attachment never changes the command's execution state.
Transport errors resume collection from the last committed sequence.

`output.go` appends host output before advancing the database collection cursor.
Flush appended events before committing that cursor.
Recovery scans incomplete tails and deduplicates events by action, boot, and sequence.
Commit final status separately from output completeness when retained output contains gaps.
Only one collector owns an action; viewers read the shared host copy.
Slow viewers never apply backpressure to guest processes.

### 6.10 `internal/plane/reconcile.go`

```go
Reconcile():
    load unfinished operations, active machines, and nonterminal actions
    verify process identities, sockets, network ownership, and disk paths
    inspect Firecracker and guest health without assuming readiness
    compare machine, boot, and guest-process identities
    resume safe lifecycle phases or record uncertain outcomes
    inspect accepted commands by their existing IDs
    restart collectors; permit new writes only after relevant checks finish
```

Probe process identity using PID and process start time, not PID alone.
Existing recorded sockets must also identify the expected machine.
Missing guest health never proves that its command stopped.
A lost guest process invalidates live output ownership, even when the machine survives.
Keep that machine unavailable for new commands until uncertain children finish or it restarts.

### 6.14 `internal/vm/snapshot.go` and `manifest.go`

```go
Snapshot(operation):
    acquire lifecycle ownership; block new platform actions
    request guest drain with a bounded deadline
    collect final outcomes and retained output; close action streams
    pause guest; copy matching disk; save memory and machine state
    flush artifacts; publish manifest last

    require original machine stopped; verify saved artifacts and compatibility

    copy saved disk to the expected runtime path
    recreate saved network; launch Firecracker; load saved state
    assign fresh boot ID through guest bootstrap; clear old connection state
    reopen admission; collect health; publish running observation
```

Drain timeout leaves the guest running and reopens admission after checking operation ownership.
Failure after pausing triggers verified termination before publishing any stopped observation.
Incomplete snapshots never appear as restorable entries.
Existing snapshots and their memory files remain immutable while restored guests use them.
Restoration uses the original machine and allocation, including a previously deleted record.
Reject conflicting live resources rather than rebinding another machine's network.
Restoration explicitly replaces that machine's current working disk contents.
Retain host action history without replaying historical commands.

Firecracker requires callers to manage disk copies alongside memory and device state.
Restored network connections may fail, so attachment always establishes fresh connections.
See [Firecracker snapshot documentation](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md).

### 6.16 `internal/guest/admission.go` and `journal.go`

`admission.go` owns the command slot, active file-operation count, and drain gate.

Bind the gate to an operation identifier; retries cannot unlock another operation's gate.

`journal.go` persists normalized requests before any execution side effects.
The same identifier and fingerprint returns the existing action.
A different fingerprint returns a conflict.
Check existing identifiers before reserving command slots or rejecting closed admission.
Journal states distinguish accepted, starting, running, completed, failed, cancelled, timed_out, and uncertain.
Never claim exactly-once execution across crashes between journaling and process launch.
Unknown launch evidence must remain uncertain until inspection or machine restart resolves it.

### 6.17 `internal/guest/runner.go`

### 6.18 `internal/guest/files.go`

Reads return bounded bytes, offset, length, and end-of-file information.

### 6.19 `internal/guest/output.go` and `stream.go`

`stream.go` attaches only to an existing action using its boot identity and cursor.

## 7. HTTP contracts and stream messages

An API is the request contract between programs.
Version both HTTP interfaces under `/v1`.
All timestamps use UTC; all payloads use JSON unless returning explicit file bytes.
Machine names resolve to immutable identifiers before mutation admission.
Every mutation includes a stable `request_id` or `action_id`.
Duplicate identifiers return existing records when request fingerprints match.
Unsupported transport modes return a structured error before changing execution behavior.

| `POST /v1/machines/{vm}/restore` | Request ID, snapshot ID | `202 Operation` |

| Method and path | Purpose | Response |
| --- | --- | --- |

The guest never initiates a connection to the control plane.

### 7.3 Errors and timeouts

| HTTP status | Meaning |
| --- | --- |
| `200` | Successful read, completed mutation, or matching duplicate result |
| `202` | Accepted work continues independently |
| `400` | Invalid parameters, encoding, or unsupported command shape |
| `404` | Unknown machine, action, operation, or file |
| `409` | Busy command slot, conflicting lifecycle work, stale identity, or fingerprint mismatch |
| `413` | File, message, or input exceeds configured limits |
| `429` | Host or guest admission limit reached |
| `503` | Guest unavailable or reconciliation prevents safe admission |
| `504` | Request deadline expired; inspect returned identifiers before retrying |

Use error codes to distinguish retryable transport failures from definite request rejection.
HTTP timeouts never establish whether a mutation executed.
Action execution deadlines remain explicit command parameters.
Return the accepted identifier whenever known, including error responses.

### 7.4 WebSocket envelopes

Use HTTP/1.1 upgrade for the initial implementation.
HTTP listeners produce `ws` connections; HTTPS listeners produce `wss` connections.
Keep ordinary requests usable while another connection streams.

```json
{"type":"output","action_id":"a1","boot_id":"b1","seq":12,"stream":"stdout","data":"aGkK"}
{"type":"gap","action_id":"a1","boot_id":"b1","first_available":30,"lost_through":29}
{"type":"exit","action_id":"a1","boot_id":"b1","seq":45,"exit_code":0}
{"type":"input","action_id":"a1","boot_id":"b1","input_seq":3,"data":"eWVzCg==","eof":false}
{"type":"input_ack","action_id":"a1","boot_id":"b1","input_seq":3,"status":"delivered"}
```

Output event numbers increase across both output channels.
Input sequence numbers use a separate counter.
`after=N` requests events strictly after N; new readers use zero.
`NextSeq` supplies the next request's cursor, matching the last delivered sequence.
Without new events, preserve the cursor unless an explicit gap advances it.
The host persists received output before advancing its collection cursor.
After exit, collect through the final sequence before closing a successful stream.
If output expires, preserve terminal status and mark output incomplete.
Automatic reconnect never creates another action or resends uncertain stdin.

## 8. Lifecycle rules and complete flows

### 8.1 State tracking without a transition matrix

Machine observations distinguish stopped, starting, ready, draining, snapshotting, stopping, restoring, deleted, and unknown.
Creation and deletion progress live in their operation records.
Errors belong to recorded operations alongside their last confirmed machine observation.
Do not replace a known running process with a stopped claim after HTTP failure.
Each lifecycle operation owns one machine until completion or explicit recovery resolution.
Reject conflicting requests instead of queuing unexpected future lifecycle changes.

Action records distinguish accepted, starting, running, succeeded, failed, cancelled, timed_out, interrupted, and uncertain.
Guest terminal command outcomes map into the corresponding host action states.
Nonzero process exit records failure while preserving the actual exit code.
Machine termination interrupts active commands; uncertain launch evidence remains uncertain until resolved.
Read operations and SSH sessions do not change machine lifecycle state.

### 8.2 Create and start

1. CLI sends a named machine specification with a stable request identifier.
2. The host reserves its identity, addresses, and creation operation transactionally.
3. A worker copies the base image and injects guest configuration.
4. Creation completes with a stopped machine and persistent writable disk.
5. Start reserves host capacity and records a new boot identifier.
6. The worker creates networking and starts detached Firecracker with unique runtime paths.
7. It waits for health, bootstraps identity, and verifies the returned guest endpoint.
8. The host publishes readiness only after the tool server confirms admission.

SSH readiness remains separately observable; tool readiness must not imply successful login.
Stop and later start preserve working files but terminate previous guest processes.

### 8.3 Execute, detach, and collect

1. CLI generates an action identifier and submits executable arguments without shell interpolation.
2. The host reserves the command slot and persists the normalized request.
3. The guest journals acceptance and starts the command independently of HTTP lifetime.
4. The CLI receives the action identifier and may exit immediately.
5. The host collector polls output or attaches an optional guest WebSocket.
6. Watch requests read host output using their own independent cursors.
7. The guest records exit, final output position, and any execution error.
8. The host collects the terminal outcome and releases the active command slot.

If acknowledgment disappears, inspect the same action identifier before any execution retry.
If the guest restarted, retain uncertainty rather than launching replacement work.

### 8.4 File reads and writes

Reads use offset and size limits through ordinary HTTP requests.
Writes reserve an action identifier before forwarding replacement bytes.
The guest stages the replacement, publishes it, and records the outcome.
A retry returns the recorded outcome without applying the write again.
An incomplete journal requires destination inspection; concurrent SSH edits can prevent certainty.
Large transfers use SSH tools instead of extending the bounded file interface.

### 8.5 Watch, input, and cancellation

Watch polls machine and action history once per second.
It displays new output without owning command execution or guest transport lifetime.
Input requests use explicit sequences and optional end-of-input markers.
The control plane serializes input through the active stream or HTTP fallback.
Cancellation targets the existing action, independently of whether output currently streams.
Natural completion racing with cancellation returns the recorded terminal outcome.
Detaching watch never sends cancellation or end-of-input implicitly.

### 8.6 Control-plane restart

1. Shutdown stops admission, saves progress, and closes collectors without stopping machines.
2. Restart acquires the host lock and reads unfinished records.
3. Reconciliation verifies surviving processes against saved machine identities.
4. It compares guest identities and inspects existing command identifiers.
5. Collectors resume from committed output positions through either transport.
6. Admission reopens separately for each reconciled machine.

A failed machine must not block healthy machines from becoming usable.
Record stale observations with their timestamps until fresh evidence arrives.
Database loss blocks new durable mutations and dispatch without confirmed reservation evidence.
Already accepted guest commands continue independently; bounded output retention still applies.
Reconnect with bounded backoff, inspect uncertain commits, then reconcile before reopening admission.
Return unavailable errors instead of presenting unpersisted observations as durable state.
Restarting the control plane and restarting PostgreSQL require separate recovery tests.

### 8.7 Snapshot and restore

1. Snapshot admission reserves the lifecycle operation and closes guest mutation admission.
2. Guest drain waits for commands and file operations within the configured deadline.
3. The host collects results, closes streams, and pauses the machine.
4. It captures matching disk, memory, and device-state artifacts in a staging directory.
5. It publishes the completed snapshot, then confirms machine termination.
6. Restore requires the original machine stopped and the saved allocation available.
7. The host restores files and starts a new Firecracker process from saved state.
8. Bootstrap establishes a new boot identity before reopening mutation admission.
9. Fresh connections resume health collection; old action history stays historical.

Users must finish SSH activity before snapshotting.
Draining cannot account for interactive processes outside platform action ownership.
The host database stays outside snapshots and requires separate backup.
Snapshot completion and machine termination require separate durable confirmations.

### 8.8 Stop and delete

Stop first blocks new actions, then terminates the verified machine process.
It retains the disk, network reservation, snapshots, and host history.
Delete requires confirmed termination and removes only that machine's runtime files.
Retained snapshots prevent releasing allocations needed for later restoration.
Repeated completed operations return their recorded results without repeating cleanup.

## 11. Testing strategy

Testing is part of the architecture and every implementation milestone.
Use [TESTING.md](../../TESTING.md) as the canonical explanation of adopted testing techniques.
Astra owns testing across every row below; named production owners support required refactors.
Tests must verify observable behavior, durable effects, or recovery invariants.
Avoid tests that merely repeat implementation steps or assert private call order.
Prefer a failing regression test before fixing a reproduced defect.
Do not add abstraction solely to increase a coverage percentage.
Each technique needs a named risk, readable example, and maintenance rationale.
Document why simpler existing checks cannot adequately cover that risk.

### Selected approach and limits

Start with readable behavior tests using real local components where practical.
Add controlled failure and crash-reopen checks at actual durability boundaries.
Safety checks verify that forbidden outcomes never occur within exercised scenarios.
Progress checks verify recovery under explicitly stated healthy conditions and bounded deadlines.
Test healthy guests' progress while another guest remains permanently unreachable.
Do not require all failures to disappear before testing independent machines' availability.

Modified Condition/Decision Coverage (MC/DC) examines each condition's independent effect on decisions.
Use targeted condition-independence examples for admission, destructive cleanup, and snapshot publication decisions.
Record each condition, test pair, expected decision, and impossible input combinations.
These examples do not establish repository-wide MC/DC coverage.
Go statement coverage does not measure condition independence or prove recovery correctness.
Keep defensive checks even when coverage cannot exercise them naturally.

Build a focused custom simulator alongside the first production admission decisions.
Use the shared core, explicit event queue, logical time, and controlled effect outcomes.
The research document defines boundaries, crash semantics, replay evidence, and tool alternatives.
Start with ordinary Go; do not patch its runtime or emulate virtual machines.
M1.4 requires lost-response replay, conflicting retries, crash reconstruction, and real PostgreSQL parity.
Verify a deliberate temporary defect fails the expected invariant; restore correct behavior afterward.
Retain the detector scenario, not intentionally broken production code.
Expand lifecycle, launch uncertainty, output, transport, and snapshot scenarios alongside their implementation.
Random seeds alone cannot control operating-system scheduling or guarantee reproducible concurrent execution.
Keep actual subprocess, storage, transport, race, and privileged machine checks.
Keep narrowly useful fuzzing optional until an implemented decoder or parser warrants it.
`TESTING.md` explains examples, source inspirations, and limitations without copying another project's testing scale.

### Failure injection cases

1. Lose a command's acceptance response after the guest starts execution.
2. Crash between accepted journaling and process-identity recording.
3. Crash after output append but before the host cursor transaction commits.
4. Restart the control plane while two guest commands continue running.
5. Restart `vmagent` while a child may survive; prohibit blind replay.
6. Drop a WebSocket after output delivery but before cursor persistence.
7. Lose an stdin acknowledgment after the guest receives its bytes.
8. Exceed output limits while no viewer or collector remains connected.
9. Delete one stopped guest while another streams output.
10. Interrupt snapshot publication before the manifest becomes complete.
11. Restore older files while preserving newer host action history.
12. Submit old-boot observations after restoration; reject them without state changes.

## 13. Risks, open details, and decision checkpoints

### Reliability risks

- A crash can separate accepted journaling from actual command launch.
  Resolve uncertain evidence explicitly; this design does not promise exactly-once execution.
- Output retention bounds can remove data before host collection resumes.
  Report gaps while preserving terminal outcomes and retained positions.
- SSH activity bypasses action ownership and snapshot admission.
  Users coordinate manual work before file replacement or snapshotting.
- Guest restart may leave surviving descendants without reliable process ownership.
  Block replacement commands until inspection or machine restart resolves uncertainty.
- Long-lived snapshots preserve old files and connection state.
  Rebootstrap identities, reconnect transports, and keep host history independent.
- Resource exhaustion can prevent journaling and complete snapshot publication.
  Reserve capacity, reject admission, and keep partial artifacts distinguishable.
- Simulated adapters can misrepresent real commits, pending work, or recovery evidence.
  Require contract parity and real fault checks; document every modeled limitation.
- A simulator can grow faster than the platform it should explain.
  Add capabilities only alongside production risks, preserving a readable first scenario.
- PostgreSQL adds independent availability, backup, migration, and connection-management responsibilities.
  Database failures must not imply that guest execution stopped.
