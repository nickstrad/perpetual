# V1.2 architecture

The host is the computer running `perpetual`, the command-line tool.
A virtual machine runs its own operating system inside the host.
The guest means everything running inside that machine.
`agentd` is a background host service that outlives command-line sessions.
SQLite stores the task queue and run history on the host.
A WebSocket lets both sides send messages through one persistent connection.
`vmagent` manages guest execution; `fx` is the initial coding agent.
Firecracker manages virtual machines; other machine managers could follow later.
A snapshot saves guest memory, disk, and machine state for later restoration.

```text
+------------------------------------------------------------------------+
| HOST                                                                   |
|                                                                        |
| You --> perpetual                                                      |
|            |                                                           |
|            | commands / attach / detach                                |
|            v                                                           |

|            |  <------> Host log files                                   |
|            |                                                           |
|            +-- machine control --> Firecracker                          |
|            |                           |                               |
|            |                           | manages                       |
|            |                           v                               |
|            |        +-----------------------------------------------+  |
|            |        | GUEST                                         |  |
|            |        |                                               |  |
|            +=======>| vmagent                                       |  |
|            |<=======+    |                                          |  |
|            |        |    +--> runner --> fx or another program      |  |
|            |        |    |                   |                      |  |
|            |        |    |                   v                      |  |
|            |        |    |              /workspace                  |  |
|            |        |    +--> local run record and buffered events  |  |

|            |                                                           |

  =====  Persistent WebSocket over the private host/guest network link

  Host --> guest: start, status, explicit cancel, supported input
  Guest --> host: acceptance, output chunks, progress, final outcome

  fx --> host internet connection --> Vercel AI Gateway --> AI model
```

## Ownership and attachment

`agentd` starts independently and accepts connections from successive CLI sessions.
It owns the queue, assigns run identifiers, and opens the guest WebSocket.
`vmagent` owns child processes independently of that connection.
The guest keeps execution records, but the host owns the task database.

`perpetual run` requests execution and returns a run identifier.
`perpetual run attach ID` replays saved output, then follows new events.
Detaching closes the viewer; only an explicit cancel command requests termination.
Neither CLI disconnection nor host service restart cancels guest execution.
Stopping or losing the virtual machine still interrupts its programs.

The first version retains one guest and one active run.
Machine identifiers prepare routing for additional guests later.
Other guest images must provide `vmagent` and the same message contract.

## Connection recovery

The guest records acceptance before launching work and rejects duplicate run identifiers.
Numbered events let the host acknowledge storage and request missing output.
During disconnection, the guest buffers events locally and continues executing.
After reconnection, both sides reconcile active runs before dispatching more work.
An uncertain delivery never triggers an automatic duplicate execution.
Bounded buffers discard oldest output when full and report gaps upon reconnection.
The guest retains final outcomes separately until the host acknowledges them.

Streaming remains optional; completed results follow the same connection.
Interactive input requires program support; WebSockets alone cannot make `fx` interactive.

## Snapshots

Saving requires an idle guest and the host's acknowledgment of outstanding results.
Then the host requests key erasure, saves the guest, and stops it.
Restoration reconnects communication and supplies credentials again.
Guest snapshots exclude the host database and logs; back those up separately.
The host assigns each restored guest a new identity before accepting events.
This prevents restored records from overwriting newer host history.

## Biggest risks

- Connection failures create uncertainty about whether work started or finished.
  Reconciliation must prevent duplicate execution and preserve final outcomes.
- Restoring guest code can move backward while host history moves forward.
  Show the snapshot origin when reporting restored workspaces.
- Guest memory may retain credentials after attempted erasure.
  Treat snapshots as sensitive and authenticate the private WebSocket connection.

## Pros

- Users can leave and reattach without supervising long runs.
- Host storage keeps task history available while guests stop or disappear.
- One connection supports commands, live output, and future interactive programs.

## Cons

- A background service adds installation, startup, and recovery work.
- Extended outages can lose buffered output, despite continued execution.
- Separate host records and guest files complicate backup and restoration.
