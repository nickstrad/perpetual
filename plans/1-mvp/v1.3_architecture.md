# V1.3 architecture

The host runs `perpetual`, the command-line tool, and the background service `agent-plane`.
A control plane coordinates machines, commands, and recorded state.
`agent-plane` provides that control plane for one or many agents.
A sandbox is a virtual machine containing programs and their working files.
Each sandbox runs `vmagent`, which owns execution and reports its state.
SQLite stores the host's machine registry, task queue, and run history.
A WebSocket lets both endpoints stream messages through one open connection.
HTTP carries individual requests without requiring a continuously open connection.
Firecracker manages sandbox machines; other machine managers could follow later.

## State ownership

The CLI always talks to `agent-plane`, including during attachment.
The control plane alone writes the host database.
CLI commands change requested state; guest reports change observed state.
For example, requesting cancellation leaves execution active until the guest confirms termination.

Each machine record stores its identity, address, creation time, and last contact.
It also tracks boot identity, lifecycle status, active run, and snapshot origin.
The host assigns identities; each restart or restoration receives a new boot identity.
The control plane rejects reports from obsolete boots.
It validates guest addresses against the machines it manages.

`vmagent` registers after startup and periodically sends health and execution updates.
It reports completion without requiring an attached CLI.
The host persists updates before acknowledging them; guests retry unacknowledged reports.
Run identifiers and numbered updates prevent duplicate execution and duplicate records.
State revisions prevent competing CLI commands from silently overwriting newer decisions.

## Attach and detach

`perpetual --watch <vm>` and `perpetual -w <vm>` attach to sandbox output.
Watch shows machine status, replays available output, and follows subsequent runs.
It waits when idle; it never starts a task implicitly.
Initially, watch displays output only; interactive input requires explicit future support.

The control plane resolves the guest address and opens its WebSocket.
It relays output through a separate CLI WebSocket.
Several viewers share one guest stream; each viewer receives its own copy.
The last viewer's departure closes the guest stream.
Ctrl-C detaches the CLI; explicit cancellation controls execution.
Guest state reports continue through HTTP while nobody watches.

## Failure and recovery

Guest execution survives CLI disconnection and control plane outages.
Guests retain pending results and bounded output locally until communication resumes.
The host retrieves retained logs after completion, even without viewers.
Reconnects replay output after the last received event number.
Guests report gaps when retention limits remove older output.
Slow viewers cannot block execution or other viewers.

Missed health reports mean unreachable, not confirmed stopped.
After recovery, the control plane reconciles machine and run states before dispatching work.
Each sandbox runs one task at a time; different sandboxes can work concurrently.

## Biggest concerns

- `agent-plane` becomes the shared access point; outages block commands and watching.
  Its recovery must preserve pending commands without repeating accepted work.
- Guest reports cross a security boundary and may contain misleading state.
  Authenticate both directions and restrict each guest to its assigned identity.
- Snapshots save guest files while the host database continues evolving.
  Restoration needs explicit reconciliation; separate backups must cover host records.
  Snapshot memory can retain credentials despite attempted erasure.

## Pros

- One CLI connection provides consistent access across many sandboxes.
- Background reports keep status current without permanent streaming connections.
- Independent guest execution lets users detach freely.

## Cons

- Two communication paths require retry, ordering, and recovery rules.
- Stream relaying consumes host bandwidth as viewers and guests increase.
- Arbitrary images need compatible `vmagent` installation and reachable guest networking.
